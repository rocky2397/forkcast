# Forkcast — Product & Architecture Decisions

**Date:** 2026-07-18
**Status:** Prototyping. Update this file whenever a decision changes.
**Repo:** https://github.com/rocky2397/forkcast (this clone on the RecipesDev volume is canonical)
**Companion doc:** `EPICURE_PAPER_NOTES.md` (the embeddings this app builds on)

---

## 1. Vision

A personal **food inventory app** that:

1. Tracks what ingredients I have at home.
2. Suggests **recipes I can cook right now** from that inventory.
3. **Learns my taste** from what I log (dishes cooked, meals eaten) and ranks
   suggestions accordingly.
4. Tracks **calories and macros** of everything I eat, suggests daily targets
   based on my fitness goals, and steers recipe suggestions toward hitting
   those targets.
5. Runs on my **phone**; a login-based **website first** is acceptable
   → built as a **PWA** so the website is installable on the phone with no
   rewrite later.

---

## 2. Honest assessment (Claude's opinion, agreed as framing)

- The idea is solid and buildable, but it is **four products in one**:
  inventory tracker, recipe recommender, taste learner, macro coach.
  The main risk is scope, not feasibility → we phase it (Section 5).
- The **Epicure embeddings are an unusually good fit** for the taste-learning
  and substitution features — they were literally built for "what pairs with /
  substitutes for X" queries.
- Epicure **does not solve** recipes, quantities, or goal-setting. Those are
  separate subsystems we build conventionally.

### Where Epicure helps directly

| Feature | Mechanism | Model |
|---|---|---|
| Taste profile | User taste vector = time-decayed mean of embeddings of ingredients in liked/cooked dishes; rank recipes by cosine similarity | Cooc (recipe-context is the right notion of "my kind of cooking") |
| Substitutions | "Recipe needs basil, you have tarragon" → Chem nearest neighbours filtered to inventory | Chem |
| Shopping suggestions | "Buy X to unlock N more recipes" → Cooc neighbours of current inventory | Cooc |
| Cuisine exploration | SLERP steering ("more Mediterranean this week") | Any; Chem has sharpest directions |
| Nutrition vocabulary | The 1,790 canonical ingredients are already anchored to USDA FoodData Central | All (shared vocab) |

### Gaps Epicure does NOT cover (we build these)

1. **No recipes** — it is ingredient-level only. We need a recipe corpus
   normalized to the 1,790-ingredient vocabulary. *This normalization is the
   single biggest data-engineering task in the project.*
2. **No quantities** — macro tracking needs portion parsing
   ("200g chicken breast") + USDA per-100g nutrient data.
3. **No input normalization** — mapping free-text user input ("half a jar of
   passata") to canonical ingredients needs an LLM call (Claude Haiku-class,
   cheap) with fuzzy string matching as fallback/cache.
4. **No goal logic** — daily calorie/macro targets come from standard formulas
   (Mifflin-St Jeor BMR × activity factor, protein by g/kg bodyweight,
   cut/bulk adjustment). Transparent formulas, no ML — a feature, not a gap.

| D6 | Taste model | *(ranking replaced by D31)* **Embedding-centroid ranking** (cosine to time-decayed user taste vector), not collaborative filtering / trained recommender | Single-user app = no collaborative data; centroid approach is explainable and works from the first logged meal |
| D7 | Goal targets | **Formula-based** (Mifflin-St Jeor + activity + goal), user-overridable | Transparent; fitness users want to see the math |
| D8 *(added 2026-07-18, amended same day)* | Inventory input | **Photo-based logging is a core input method** (not just text): snap a picture of groceries → Claude vision extracts a structured item list → user confirms/edits → items committed to inventory. **Vision model: `claude-haiku-4-5`** with structured outputs (`messages.parse()` + Pydantic schema) so extraction returns validated JSON, never free text; optional "rescan with better model" button falls back to `claude-opus-4-8` for garbled results | User requirement. Always show the confirm screen before committing — counting/occlusion errors in photos are expected |
| D9 *(added 2026-07-18, amended same day)* | Label nutrition | **Barcode-first, vision-fallback** for packaged food: (1) scan the barcode in-browser (free JS library, no API call) → look up **Open Food Facts** (free, open database, strong German coverage) → per-100g nutrition saved to `products`; (2) only if the product is missing or has no barcode, photograph the **Nährwerttabelle** → `claude-haiku-4-5` extracts per-100g values (kJ/kcal, Fett, davon gesättigte Fettsäuren, Kohlenhydrate, davon Zucker, Eiweiß, Salz) + portion size → confirm → cached in `products` so each product is handled once | EU regulation 1169/2011 standardizes the table format, so even a small vision model reads it reliably; barcode-first makes the majority of packaged-product lookups cost exactly zero. Complements USDA rather than replacing it: USDA covers whole ingredients (chicken, lentils), products cover branded/packaged foods (protein bars, sauces, quark) that USDA maps poorly. Rejected: self-hosted vision models / Tesseract OCR (pennies saved, real ops burden, worse accuracy). *Shipped 2026-07-19:* in-browser detection uses the native `BarcodeDetector` API (no JS library needed) where available, with a self-hosted zxing WASM fallback (code-split, ~1 MB, loaded on first scan, precached for offline) for Safari/iOS which lacks the API — so the barcode read is free on every browser; only when neither decodes does the photo go to `/api/nutrition/scan`, where Haiku reads the printed EAN digits (only when fully legible — never guessed) and/or the Nährwerttabelle in one call. A resolved barcode makes Open Food Facts authoritative and caches into `products`; verified live (Nutella EAN → OFF exact; label photo → 539/6.3/57.5/30.9 per 100 g, matching OFF digit-for-digit) |
| D10 *(added 2026-07-18)* | Storage policy | **Everything lives on the external SSD — no persistent storage on the internal PC drive, including caches.** All tool caches are redirected via env vars (see Section 8): HuggingFace model downloads (`HF_HOME`), pip (`PIP_CACHE_DIR`), npm (`npm_config_cache`), Python venv and `node_modules` inside the project, database file(s) and recipe corpus in a project `data/` dir | User requirement. Without redirection, the Epicure weights alone would land in `~/.cache/huggingface` on the internal disk. Honest caveat: small *ephemeral* OS temp files during process runtime (`/tmp`) can't be fully avoided at the OS level — the policy covers all persistent storage |
| D11 *(added 2026-07-18)* | Dev volume | **APFS sparse-bundle disk image stored on the ExFAT SSD**, mounted as the working volume for development | The SSD is ExFAT (verified via `diskutil`), which lacks symlinks and Unix permissions — breaking Python venvs and npm's `node_modules/.bin`. A `.sparsebundle` file lives on the SSD (all bytes stay physically there), is non-destructive, keeps the SSD Windows-readable, and mounts as a real APFS volume where all tooling works. Rejected: reformatting to APFS (destructive, kills Windows compat); staying on ExFAT with workarounds (fragile). Trade-off accepted: the image must be mounted before working (scripted in `dev.sh`) |
| D12 *(added 2026-07-19)* | Calorie/macro targets | **Mifflin-St Jeor BMR × activity factor = TDEE, adjusted by goal (cut −15% / maintain / bulk +10%). Macros: protein 1.8 g/kg body weight, fat 25% of kcal, carbs the remainder. Metric units.** Profile is a single local row (sex, age, height, weight, activity, goal). Recipe cooks derive macros from the recipe row (per serving); ad-hoc meals are quick-added with manual macros | Mifflin-St Jeor is the standard, best-validated resting-energy equation for the general population; 1.8 g/kg protein sits in the evidence-backed 1.6–2.2 range for training people; fat at 25% kcal keeps hormones happy while leaving carbs for training fuel. Manual quick-add is the honest MVP until D9 (barcode + Nährwerttabelle scan) feeds the same path automatically |
| D13 *(added 2026-07-19)* | Substitution suggestions | *Status 2026-11-14: superseded in part by D28. The stage 2 eval found the unclassed rank path wrong 74 times in 98; D28 removes it and widens the class map.* **Rank-gated, class-guarded stand-ins from the inventory** for a recipe's missing ingredients: candidate must rank within the missing ingredient's top-200 cooc AND top-400 chem neighbors (forward direction only); a hand-curated coarse food-class map (meat, seafood, herb, allium, citrus, dairy, sweetener, grain) must agree — same class relaxes the gate to cooc ≤ 400 (class already vouches for "same kind"), class mismatch rejects outright, both-unclassed uses the strict dual gate. Staples excluded on both sides. Shown as "needs X — try Y" chips in the feed and hints in the recipe detail | Ranks, not raw cosines: cosines aren't comparable across ingredients (hub effects, §8) — yogurt~sour_cream scores 0.084 while carrot~salmon scores 0.136. Embeddings alone can't separate complements from substitutes across food kinds: duck↔ginger passes every rank gate in both directions (fwd 17/85, rev 70/44) because they genuinely share flavor chemistry — the class map is the missing orthogonal signal, and it also recovers within-class pairs the chem gate missed (rice→couscous, beef→lamb, scallion→onion, maple_syrup→honey). Precision over recall throughout: a wrong suggestion costs trust, a missed one costs nothing. Validated on 17 regression pairs (all pass) + live probe (turkey/duck/pork→chicken, celery→carrot, lemongrass→ginger; salt→ginger bug fixed by excluding staple missings) |

Accepted for trusted-friend demos only: all visitors share the single-user data (inventory, profile, meal log, taste), vision endpoints run on the owner's API key, the URL is random per run and dies when the tunnel stops, and the Mac must stay awake. `data/forkcast.db` is backed up before demo sessions | Free, no account, one command, nothing deployed. Rejected for now: real hosting (Fly.io/Railway) — that properly requires the deferred auth + per-user data slice first, so strangers can't mutate the owner's data or spend their API credits |
| D15 *(added 2026-08-01)* | Permanent hosting | *Status 2026-11-14: prepared but never deployed — no Render service exists, and daily use runs through D18. Kept as a ready option.* **Render, Docker web service on a paid instance with a 1 GB persistent disk**, gated by a **single shared password** — not per-user accounts. Password in `FORKCAST_PASSWORD`; an HMAC-signed, HttpOnly, 30-day session cookie (`backend/app/auth.py`, stdlib `hmac` — no new dependency) guards every `/api/*` route except login/session/health; the static bundle stays open so the login screen can render; login attempts are rate-limited 10/5 min per client IP (`--proxy-headers` so the bucket is the real caller, not Render's balancer). The database is **split in two** (`backend/scripts/split_corpus.py`): `corpus.db` (87.9k recipes + 794k ingredient rows, ~130 MB, read-only, baked into the image, published as a release asset on a separate **public** data repo) and `forkcast.db` (inventory, meal log, profile, products — a few KB, on the persistent disk). `db.py` ATTACHes the corpus read-only; unqualified table names resolve across both, so no query changed. Epicure weights are prefetched at build time. See `DEPLOY.md` | Supersedes D14 for sharing that outlives a session: the tunnel needs the Mac awake and hands out a URL that dies on exit. Shared password chosen over full multi-user because per-user data slicing means a `user_id` migration across every table and query — real work, deferred until someone actually needs their own kitchen; one password already fixes the two things that made D14 unsafe to leave running (strangers mutating data, strangers spending API credits). Free tier rejected: ephemeral filesystem wipes user data on every redeploy, 15-min spin-down costs a ~1 min cold start, free Postgres expires after 30 days. Corpus split rejected alternatives: Postgres migration (rewrites all SQLite queries to move 12 rows of actual user data), Git LFS (111 MB per version against GitHub's 1 GB free bandwidth, drained by a handful of builds), rebuilding the corpus during the Docker build (pulls the food.com shards from Hugging Face and re-normalizes them — slow and over the build budget). Public data repo rather than a token in a build arg, which Render explicitly warns against since build args can persist in image layers; the corpus is derived entirely from public sources, so publishing it exposes nothing private (licence caveat: the food.com mirror states no licence, so the corpus is shared for non-commercial use only — see README) |
| D16 *(added 2026-08-11)* | First-run explanation | **A dismissible three-step walkthrough** (`frontend/src/screens/Intro.tsx`) shown once before the tabs, after the D15 password gate. Each step pairs the action with its result — photograph groceries → a checklist you confirm; a stocked kitchen → 87,861 recipes ranked by what's cookable now; rating cooks → ranking that follows your taste, and barcode/Nährwerttabelle scans that feed the macro targets. Dismissal is recorded in `localStorage` under a versioned key (`forkcast.intro.v1`), so changing the loop can re-show it; `skip for now` deliberately does *not* record, matching what the words promise. Unreadable storage (private-mode Safari) is treated as "already seen" rather than blocking the app | The app is unusable until the inventory is stocked, but the D14/D15 share links drop a newcomer straight onto an empty Today tab that explains none of that — and the payoff (ranked feed, substitutions, learned taste) is invisible until something is in the kitchen. Rejected inline hints under each control: they answer "what does this button do" but never "why is this app empty", which is the actual first-run failure. Server-side persistence rejected — with one shared account, one person dismissing it would hide it from everyone |

| D18 *(added 2026-11-14)* | Phone testing | **Tailscale serve as the daily-driver phone channel**: the Mac joins a personal tailnet and `tailscale serve --bg http://localhost:8000` publishes the backend as `https://<machine>.<tailnet>.ts.net` — tailnet-only, real TLS certificate, stable URL. The phone runs the Tailscale app on the same account and installs the PWA from that URL once; the serve config persists across reboots as long as the Tailscale menu-bar app runs at login. The D15 password gate stays on (redundant inside the tailnet, but harmless and keeps one code path) | The PWA layer (home-screen install, service worker) needs HTTPS with a cert the phone trusts, and the install must survive restarts — which rules out plain-HTTP LAN access (no PWA) and the D14 quick tunnel (random URL per run breaks the installed app). Photo intake is unaffected either way: the frontend uses `<input capture>`, not getUserMedia, so it never needed a secure context. Trade-off accepted: reachable only while the Mac is awake with the backend running |
| D19 *(added 2026-11-14)* | Inventory depletion on cooks | **"I cooked this" asks "did anything run out?"**: `POST /api/recipes/{id}/cooked` takes an optional `used_up` list of canonicals and deletes them from the inventory in the same transaction as the meal-log insert; the confirm step in `RecipeView` lists the recipe's in-inventory non-staple ingredients plus any suggested substitute (in inventory by construction, labeled "used for X"), all **unchecked by default**. Recipe detail now carries a per-ingredient `staple` flag so the client never hardcodes the staples list. Entries not in the inventory are silently ignored (stale checklist from another device must not fail the log); a body-less POST keeps the old behavior | The app's core promise — "recipes you can cook right now" — dies with inventory drift, and logging a cook was the one moment the app *knows* ingredients were consumed yet didn't act on it. Unchecked by default mirrors the D13 philosophy (precision over recall): a cook rarely finishes an item, and wrongly deleting one poisons the feed worse than keeping an empty jar listed. Staples excluded — nobody finishes the salt on one dish, and D6 already treats staples as noise. Rejected: quantity tracking (open question 2) — have/have-not plus this one-tap tick stays the honest MVP; full amounts only if this proves insufficient |
| D20 *(added 2026-11-14)* | Macro-aware ranking | **The feed is steered by what's left of today's macro budget.** `goals.macro_fit()` scores a serving 0-1 as the **cosine between its macro composition and the remaining budget's**, both expressed in *calorie* contributions (grams aren't comparable: fat carries 9 kcal/g and carb counts dwarf protein counts); exceeding the remaining calories **decays** the score by `remaining/recipe` rather than disqualifying the dish. Within each missing-count group the sort key becomes `0.6 * taste_sim + 0.4 * macro_fit` — fewest-missing still wins first. `/api/recipes/cookable` gained `macro_focus` (the macro furthest behind as a share of its target) which the feed renders as "110g protein to go today", plus a per-recipe `macro_fit` shown as a "fits macros" badge at ≥ 0.8. Steering switches off entirely with no profile, or when under 150 kcal of the day remain — then the feed falls back to pure taste ranking | Closes the loop between the two halves of the app: the macro coach (D12) and the recommender (D6) existed side by side, and the feed ignored the targets it was displaying. Cosine over calorie shares reuses the comparison the whole app is built on and needs no new data — per-serving macros and the day's totals were both already there. Taste weighted higher than macro fit deliberately: taste is learned over months, macro fit is a within-day nudge, and a protein-deficit day must not turn the feed into a list of chicken breasts. Decay over a hard calorie cap because a big dish late in the day is a worse fit, not an error — and the corpus macros are per-serving estimates, too noisy to justify a cliff. Rejected: a separate "hits your macros" tab (splits the feed the user already trusts); rejected: steering by calories alone (the thing actually missed is usually protein, not kcal) |
| D21 *(added 2026-11-14)* | Shopping suggestions | **Greedy set cover over the near-miss corpus, taste-weighted** (`backend/app/shopping.py`): take every recipe 1-3 ingredients short (`recipes.missing_sets()`, ~15k for a typical inventory), then pick repeatedly the ingredient completing the most still-locked recipes *given the earlier picks*, three by default. Counts are therefore **marginal and disjoint** — a recipe needing yeast *and* milk is credited once, to whichever lands second — so the list renders as an ordered basket ("yeast — 141 recipes", "milk — +177 more"), never as a leaderboard. Taste tilts selection only: weights are min-max normalized **within the pool** to [0.5, 1], and the number shown is the honest unweighted count. Surfaced as a section under the feed (`GET /api/shopping`), loaded independently of the recipe list, with `partial_scan` exposed when the 20k pool ceiling bites | Turns the app from reactive ("what can I cook?") into proactive ("what should I buy?") — the thing worth opening *in* the supermarket, and the last unbuilt item of Section 2's Epicure table. Set cover rather than the originally planned Cooc neighbours: the question is "which purchase completes the most recipes", which the corpus answers exactly, while embedding neighbours only answer "what goes with what" — they'd suggest plausible pantry items with no idea whether a single recipe actually becomes cookable. Greedy over exact optimum: set cover is NP-hard, greedy is the standard log-factor approximation, and a 3-item basket makes the difference invisible. Weights normalized within the pool because absolute cosines bunch near 0.9 (hub effects, paper §8 — the same reason D13 gates on ranks); an unnormalized weight would rank no differently from plain counting. Deliberately **ignores today's macro budget** (unlike D20): shopping is a multi-day decision, and tonight's remaining protein is the wrong input for it. Rejected: a dedicated tab (a new habit to form for the same recipes); rejected: one-tap "add to inventory" on a suggestion (it would record food you haven't bought — exactly the inventory drift D19 exists to prevent) |
| D22 *(added 2026-11-14)* | Tests | **pytest over the scoring logic and the HTTP surface — 66 tests, ~3 s, offline and corpus-free.** `backend/tests/conftest.py` points `FORKCAST_DATA_DIR` at a temp DB *before* importing `app.db` (`connect()` binds its default path at definition time) and names an absent `FORKCAST_CORPUS_DB`, so the legacy single-file shape creates writable recipe tables; it then seeds a 7-recipe fixture corpus shaped so the greedy basket has a known answer. Tests needing the Epicure weights carry a `needs_embeddings` marker that auto-detects the HF cache, so they run locally and skip elsewhere. API tests stub `embeddings.vocabulary()` — all that `/health` and the substitution pre-checks actually need — and skip the lifespan, which would build the real Normalizer. `pytest.ini` puts `backend` on the path so tests import `app.*` exactly as the server does | D19-D21 are exactly the kind of features where a regression stays invisible: a drifted `unlocks` count, a macro cosine that silently stops discriminating, or a substitution gate that starts accepting complements all still *look* plausible in the UI. D13's "validated on 17 regression pairs" was never committed, so that claim had quietly become unreproducible — `test_substitutions.py` now encodes those pairs and they pass. Shopping's counts are asserted against independently recomputed coverage, the only real guard against double-crediting a recipe that needed two purchases. Fixture corpus rather than the real 87.9k one: tests must run on a clean checkout with no 130 MB download, and a known 7-recipe shape makes the greedy basket's expected answer something to assert rather than to eyeball. Found while writing it: a `Secure` cookie cannot round-trip over the TestClient's plain HTTP — the app was right and the test was wrong (`FORKCAST_INSECURE_COOKIE`, as DEPLOY.md documents for LAN runs), and the secure-by-default flag now has a test of its own |
| D23 *(added 2026-11-14)* | CI | **Two GitHub Actions jobs on push and PR** (`.github/workflows/ci.yml`): backend installs `requirements.txt` + `requirements-dev.txt` on Python 3.12 and runs `pytest` with **`HF_HUB_OFFLINE=1`**; frontend runs `npm ci`, `npm run lint` (oxlint) and `npm run build`, which also type-checks since the script is `tsc -b && vite build`. The Docker image is deliberately **not** built | Offline mode is the load-bearing choice: the D22 marker makes weight-dependent tests skip, and `HF_HUB_OFFLINE=1` turns an *unmarked* one into a loud failure rather than a silent 100 MB download on every run. Verified by installing into a clean 3.12 venv with an empty HF cache — 42 pass, 24 skip. Adding the lint gate immediately earned its keep by flagging a ternary used for its side effects in `RecipeView` |
| D24 *(added 2026-11-14)* | Deterministic matching | **Equal-length ingredient spans break alphabetically, not by set iteration order** (`Normalizer.__init__` sorts on `(-len(c), c)`). Measured with `backend/scripts/normalizer_diff.py`, which exists because plausible matcher rules routinely make hundreds of strings worse | The span scan walked a list built from a `set`, so Python's per-process hash randomization decided ties: the same string matched differently from one run to the next — "bread flour" gave bread or flour, "tuna fish" gave tuna or fish, "daikon radish" gave daikon or radish. Roughly 112 strings (1,851 corpus rows) were coin flips, and the import simply froze whichever draw its process made. Alphabetical is as arbitrary as any tiebreak but it is *stable*, which is the property that matters: without it the diff script cannot distinguish a real change from noise, so this had to land before any matcher work. Rejected: picking the "better" ingredient per tie — that is the per-string curation a rank-based matcher exists to avoid |
| D25 *(added 2026-11-14)* | Compound ingredient names | **`cherry tomato`, `grape tomato` and `campari tomato` are aliases of `tomato`, and a compound alias may override a narrower word it fully contains** — but only the six names listed in `_COMPOUND_UPGRADES`. Checked across phrase variants, so the singular is seen in "yellow cherry tomatoes"; `corn flour` is deliberately excluded. Measured: 8 strings, 91 rows beyond what the aliases alone fix (`italian plum tomatoes`, `green onion tops`, `yellow cherry tomatoes`) | "cherry tomatoes" was read as the fruit in 530 corpus rows: the containment pass finds "cherry" and stops, because "tomatoes" is not itself a canonical name — only the singularized variant exposes "tomato". Both general rules were tested on all 11,384 distinct corpus strings and rejected on the evidence: **"last word wins" moves 708 strings** (garlic clove becomes the spice, salt and pepper becomes pepper) and **"longest match wins" moves 208** (bread flour becomes flour). An earlier attempt here let *every* multi-word alias upgrade and moved 177 strings / 2,610 rows, turning "wheat flour" into wheat and "tuna fish" into fish — so the set is opt-in, each entry measured. `corn flour` → cornstarch is correct alone but as an override rewrites "masa corn flour" to cornstarch. Handled in D26: the "X with Y" class |
| D26 *(added 2026-11-14)* | Connector and negation phrases | **The head of an "X with Y" phrase is the ingredient, and a negated ingredient is not an ingredient.** `_head_segment()` cuts at `with` or `in` and tries the head first, falling back to the whole string when the head matches nothing; `_strip_negations()` removes `no <x> added` and `<x> free` before matching. `cookability` (fraction of ingredients in inventory, substitutions counted at
a discount) + `taste` (cosine to user vector) + `macro fit` (how well the
recipe fills the remaining daily budget). Weights tunable; start 50/30/20.

### Data model (first cut)

- `users` — auth, bodyweight, height, age, sex, activity level, goal (cut/maintain/bulk)
- `ingredients` — the 1,790 canonical entries + USDA nutrient anchors (per 100g)
- `inventory_items` — user, ingredient_id, quantity (optional at first), added_at
- `recipes` — title, source, servings, normalized ingredient list (ids + amounts), per-serving macros (computed), cuisine tags
- `products` — label-scanned packaged foods: name, brand, optional barcode, per-100g macros (kcal, fat, saturates, carbs, sugars, protein, salt), portion size, link to nearest canonical ingredient, source photo reference
- `meal_log` — user, timestamp, recipe_id OR ad-hoc ingredient list OR product_id + amount, servings, computed macros, liked (bool/rating)
- `goals` — computed targets + user overrides, effective_from

## 6. Open questions (decide when they block work)

1. Which recipe corpus subset and how large? (Quality/curation vs coverage —
   decide during Phase 1 pipeline work after inspecting RecipeNLG.)
2. Quantity tracking in inventory: full amounts, or just have/have-not with
   staples flagged? (Start have-not + staples; amounts only if depletion
   tracking proves wanted.)
3. Barcode scanning / photo input for logging? (Phase 3+ at the earliest.)
4. Multi-user from the start or hardcode single user? (Schema supports users;
   UI can stay single-user.)
5. LLM budget: vision intake (D8/D9 fallback) and normalizer fallback are the
   only paid calls. On `claude-haiku-4-5` a scan is ~$0.005; expected total
   vision cost well under €1/month, since barcode + Open Food Facts resolves
   most packaged products for free and the `products` cache means each item
   is handled only once. (Barcode-first was promoted from open question to
   decided — see D9.)

## 7. Storage & environment setup (SSD-only, D10/D11)

### One-time: create the APFS dev volume (sparse bundle on the ExFAT SSD)

```bash
# 100 GB is a *ceiling* — a sparse bundle only occupies what's actually written
hdiutil create -size 100g -type SPARSEBUNDLE -fs APFS \
  -volname "RecipesDev" "/Volumes/Extreme SSD/RecipesDev.sparsebundle"
```

### Every session: mount before working (goes in `dev.sh`)

```bash
hdiutil attach "/Volumes/Extreme SSD/RecipesDev.sparsebundle"
# → mounts at /Volumes/RecipesDev  (code, venv, node_modules, data all live here)
cd /Volumes/RecipesDev/recipes_app
```

Unmount with `hdiutil detach /Volumes/RecipesDev` (or Finder eject) before
unplugging the SSD.

### Cache redirection (exported by `dev.sh` / `.envrc`, never set globally)

| Env var | Points to | Keeps off the internal disk |
|---|---|---|
| `HF_HOME` | `/Volumes/RecipesDev/caches/huggingface` | Epicure model weights + HF hub cache (default `~/.cache/huggingface`) |
| `PIP_CACHE_DIR` | `/Volumes/RecipesDev/caches/pip` | pip wheel/download cache (default `~/Library/Caches/pip`) |
| `npm_config_cache` | `/Volumes/RecipesDev/caches/npm` | npm package cache (default `~/.npm`) |

Additionally, by construction inside the dev volume: the Python venv
(`.venv/`), `node_modules/`, the SQLite database, the recipe corpus, and all
build artifacts. If Postgres is ever adopted (Section 4), its data directory
must be created on the dev volume (`initdb -D /Volumes/RecipesDev/pgdata`).

**Placement note:** the paper and these planning docs currently sit in
`/Volumes/Extreme SSD/stuff/recipes_app` (ExFAT side) — fine for documents.
The *code* project gets created inside the mounted APFS volume, with the
planning docs copied or moved in when scaffolding starts.

**Known limitation (accepted):** truly ephemeral OS temp files written to
`/tmp` during process runtime cannot be redirected wholesale; no *persistent*
data lands on the internal drive.

## 8. Prototype findings (2026-07-18)

Environment is live: APFS dev volume mounted, venv (Python 3.12, pinned — the
system `python3` is Anaconda's 3.8 via PATH shadowing), Epicure-Cooc weights
downloaded to the SSD HF cache, loader smoke-tested.

1. **Epicure loader verified.** `neighbors("chicken")` reproduces the paper's
   Table 6 exactly (garlic .39, onion .37, black_pepper .36, turkey .35,
   carrot .34). Vocab confirmed at 1,790.
2. **Recipe coverage validated** — see amended D1. The main risk of the
   curated-dataset plan is retired.
3. **⚠️ Shipped cuisine poles ≠ paper's.** `supervised_poles.json` contains
   "heuristically constructed" cuisine directions (model card's own words).
   SLERP toward them works mechanically but the top ranks are dominated by
   universal staples (salt, onion, garlic) — the paper's hero results
   (rice+South_Asian → dals) sit at ranks 14–25. Mean-centering does not fix
   it. **Consequence for Phase 3 (cuisine dial):** filter universal staples
   from steering results (build our own "universal" list, e.g. top-N by
   corpus frequency) or re-derive cuisine poles from tagged ingredients.
   The 0° case and plain neighbors are unaffected.
4. **Companion dataset gaps:** `vocab.csv` ships name + node IDs only — **no
   USDA/FlavorDB anchor columns** (despite the paper's claim), and no
   per-ingredient universal/cuisine tags. Ingredient-level nutrition mapping
   (needed for ad-hoc whole-food logging in Phase 2) is our own task —
   mitigated by food.com per-recipe nutrition (D1) and label scanning (D9).
5. **Alias table** is the cheapest next quality win for the normalizer:
   ~10–20 entries fix the bulk of unmatched terms (pepper, green pepper,
   cilantro, cornflour, gingerroot, cayenne, catsup, bay leaves, …), plus
   proper plural handling for multi-word terms ("bay leaves" → bay_leaf).
